Note: `kubectl run` ephemeral-pod probes were DENIED by the read-only guard, so the runtime /api/rawdata
dump was not taken; the conclusion below rests on kubectl get + kubectl logs evidence, which is decisive.

================================================================================
ANSWER: The served cert is Traefik's OWN auto-generated in-memory default self-signed
certificate (Traefik's built-in "default certificate"), selected at TLS-handshake time
because NO certificate in Traefik's store is bound to the request SNI.
It is source (iii) from the task list — Traefik's auto-generated default cert —
NOT (i) a file-provider default, NOT (ii) a traefik.io TLSStore default, and the
Gateway listener certRef (iv) is NOT being applied to these hosts.
================================================================================

WHY (the exact mechanism):
1. Traefik args (live, authoritative — pod traefik-9f4b6d9fc-fznzp):
     --entryPoints.websecure.address=:8443/tcp
     --entryPoints.websecure.http.tls=true      <-- TLS on, but with NO default certificate specified
     --providers.kubernetesgateway (+ experimentalchannel=true), --providers.kubernetescrd, --providers.kubernetesingress
   There is NO --*.defaultCertificate, NO --providers.file, NO --serversTransport, NO
   --certificatesResolvers/ACME resolver. Env has NO TRAEFIK_*/ACME/default-cert vars.
   Volumes = only data(emptyDir)+tmp(emptyDir)+SA token — NO cert secret, NO configmap mounted.
   => Traefik has NO configured default certificate and NO file/tlsstore dynamic config.

2. Dynamic config CRs: `kubectl get tlsstore,tlsoption -A` = "No resources found" (re-confirmed live).
   The ONLY traefik.io CR in the whole cluster is Middleware platform-mesh-system/cors-header.
   => There is NO tls.stores.default.defaultCertificate anywhere (rules out source ii).

3. The `*acme.ChallengeTLSALPN` provider line in the log is ONLY the TLS-ALPN-01 challenge
   responder that ships on by default; there is no certificatesResolver, so it issues nothing
   and does not create the served cert. (Rules out ACME issuance.)

4. THE ROOT BEHAVIOR — why the listener certRef never reaches these hosts:
   Traefik's kubernetesgateway provider compiles EVERY HTTPRoute attached to k8sapi-gateway into a
   router whose Rule is a HostRegexp derived from the *listener* hostname pattern, e.g.
       HostRegexp("^[a-z0-9-\.]+\.ai-trust-1\.ai-trust\.shoot\.gardener\.cc-one\.showroom\.apeirora\.eu$")
   Confirmed live: of 9226 routers built, 100% are HostRegexp(...) — ZERO Host(...) / HostSNI(...) routers.
   This happens EVEN THOUGH the instance HTTPRoutes carry a CONCRETE host in .spec.hostnames
   (e.g. q3c0weh7suf5hgjk-my-aitrust.ai-trust-1..., testai.ai-trust-1...): the wildcard listener
   ("*.ai-trust-1...") makes Traefik emit a regex-host router, not a literal-host router.
   For every such router Traefik logs (9002+ times):
       "No domain found in rule HostRegexp(...), the TLS options applied for this router
        will depend on the SNI of each request"
   MEANING: a HostRegexp router has no literal domain, so Traefik cannot statically associate the
   Gateway listener's certificateRef (secret domain-certificate) with a specific SNI/router in its
   TLS certificate store. At handshake time Traefik looks up a cert by the client's SNI; finding no
   store entry keyed to that domain, it falls back to its BUILT-IN auto-generated default self-signed
   certificate (Go/Traefik "default" cert — CN of the served leaf here is ai-trust-1-mesh from the
   self-signed material, i.e. the cluster's default-cert flow). No log line ever references
   "domain-certificate" or "cert-p1" — Traefik never loads the listener secret as a store cert for
   these regex routers.

5. This DIRECTLY explains the failed Phase-2 trial: repointing terminate-wildstar.tls.certificateRefs
   from domain-certificate -> cert-p1 (listener stayed Programmed=True) had NO effect on the served
   cert because Traefik was never serving the listener certRef for these hosts in the first place —
   it serves the SNI-fallback default cert. Changing the certRef on a listener whose routes compile to
   HostRegexp does not change the SNI-keyed store, so the served cert stayed self-signed. (The prior
   backup README's "Flux reconciled the patch away" theory is not the operative cause — the listener
   certRef simply is not consulted for regex-host routers.)

PRECISE CONFIG PATH/VALUE THAT CONTROLS THE SERVED CERT:
- What controls it today: NOTHING explicit. Because (a) no defaultCertificate is set on the websecure
  entryPoint / no TLSStore "default" exists, AND (b) all routers are HostRegexp with no literal domain,
  Traefik serves its internal auto-generated default self-signed cert for every SNI. The served leaf
  CN=ai-trust-1-mesh / issuer "Standard Platform Mesh Local CA" is the self-signed material that the
  environment seeded as Traefik's effective default.
- The knob that WOULD control it (for the GOAL, not applied here): set Traefik's DEFAULT certificate
  to cert-p1, via ONE of:
    (a) a traefik.io TLSStore named "default" with defaultCertificate.secretName referencing the LE
        secret (needs the secret readable in Traefik's namespace/default), OR
    (b) the traefik entryPoint default cert (tls.stores.default.defaultCertificate in a file/CRD
        provider), OR
    (c) make Traefik build literal Host() routers (concrete listener hostnames instead of the wildcard
        "*.ai-trust-1..." listener) so the listener certRef is actually bound per host — this requires
        the HTTPRoutes to attach to a listener whose hostname is literal, which is a structural change
        to how the "infra" chart templates k8sapi-gateway.
  Any of these is a Helm-values / dynamic-config change owned by Flux HelmRelease "infra" (gateway) or
  "traefik" (data plane) — see backup-traefik/README.txt for ownership + rollback. (NOT applied.)
